# Phase 1C verification and rollout notes

Status: implementation is present but production readiness is not established. Authenticated browser acceptance, representative external integrations, production schema/journal comparison and the Phase 1B membership reconciliation gate remain open.

## Implemented

The project workspace shows organization-scoped project, client, task, milestone, team, audit, quotation, invoice and expense information, with financial and quotation reads gated by existing permissions. Task creation, edits, assignment, statuses and progress comments use server-side authorization, validation, organization constraints, live Clerk assignee verification, audit events and retry or optimistic concurrency handling. The task list filters by project, assignee, status and priority. Milestones support deliverables, responsibility, due dates, evidence, administrative approval and rejection with feedback and resubmission. Administrators can transition projects; closing with unresolved required work requires a recorded exception. Existing project activation remains separate. There are no task-triggered financial actions.

## Migration

`drizzle-current/0008_project_execution.sql` follows local 0000–0007. It adds milestone fields and required-work flags, an organization-scoped staff foreign key, and database guards that lock the project row when project tasks or milestones change. A transition function locks that same row, checks required work, and records the transition and any exception. Existing tasks and milestones default to required; business owners must review the impact before rollout. The triggers also affect other database writers to project tasks or milestones, so integration and database privileges require review. The SQL function assumes execution through the authorized application; restrict direct database access appropriately. The migration was applied only to the isolated test fixture. No production migration was run.

In a new empty database `phase1c_history_fixture` in the separate approved test Neon project, the real local 0000–0007 SQL chain was applied in order. Synthetic pre-0008 tasks and milestones were inserted. Within a rolled-back PostgreSQL transaction, unmodified 0008 marked both historical records required. A separate rolled-back experiment changed only the migration-time column defaults to false and subsequently changed the defaults for new inserts to true: legacy records remained false and newly inserted synthetic records were true. This is a **proposal**, not an applied change to 0008. Both 0008 experiments were rolled back; the fixture was not reset. Previous two-connection tests cover the original guards, but the proposed revision still needs a complete rehearsal after the deployment mapping and migration strategy are approved.

Recommended rule: existing work has no newly imposed completion requirement until staff explicitly review and mark it required; newly created work defaults to required, with an explicit optional choice. A false value in this proposal means no new requirement is enforced, not that someone has reviewed the historical work. Review and label historical records separately before relying on their classifications. If 0008 is confirmed never deployed anywhere relevant, revise it to add the two columns with `DEFAULT false NOT NULL`, then set both defaults to true before new application writers run. Recreate the migration snapshot/hash as appropriate and rerun the full chain. If any deployment has applied 0008, do not rewrite it or blindly mark rows optional: use a separately reviewed correction and verified evidence to distinguish historical records from subsequently created or deliberately classified work. No safe automatic distinction currently exists in the schema.

The trigger applies to every insert, update and delete of project-linked tasks and milestones, rejects reparenting, and blocks changes on closed/archived projects. Repository inspection found Phase 1C actions as the relevant project task/milestone writers; direct SQL integrations and deployed code have not been fully inventoried. In particular, editing milestones on completed projects and cascading operations may be blocked; rehearse every external writer and rollback under the actual database role. The transition function still requires database privilege review because direct function callers are not authenticated by Clerk.

### Staff reconciliation

An administrator-only **Refresh staff from Clerk** action is available on Leads. It checks the administrator's current Clerk membership, enumerates members with an upper bound, checks each candidate directly against Clerk, creates/updates local staff records including roles, and marks confirmed absent members removed. A locally suspended record remains suspended. Database observation timestamps prevent an older overlapping refresh from overwriting a newer refresh. Failures produce a retry message; completed per-person writes are not rolled back as a group. Normal task, milestone and lead assignment retains its independent live Clerk check and fails closed if Clerk cannot be reached.

Disposable PGlite tests with mocked Clerk responses passed for additions, removals, reinstatement, role changes, missed-event recovery through a later refresh, preserved suspension, provider failure, cross-organization isolation, administrator denial and protection against an older observation. This is an **operator-triggered reconciliation**, not a webhook or scheduled job; no automatic event delivery, freshness guarantee or real-Clerk integration is claimed. Membership can change between the Clerk check and the database mutation. The staff list can be stale until refreshed, and no local database or Clerk operation can provide an atomic cross-service guarantee. Large organizations may hit execution or provider limits; test expected staff counts and failure recovery. Review whether on-demand reconciliation meets the business's required recovery time before treating the Phase 1B gate as closed.
