# Lead ownership and rollout review

The Phase 1B migrations add nullable organization ownership to website leads, real-estate enquiries, and property-listing enquiries. They do not backfill historical records. The lead dashboard, list, updates, and conversion exclude leads with unknown ownership. Property and estate intake remain separate source records; Phase 1B does not duplicate or import them into the lead list.

Before any rollout, review migrations 0005 and 0006 and test on an isolated PostgreSQL database with a representative schema and synthetic data. Apply migrations before deploying code that selects or inserts the new columns; deploy both together through the normal reviewed release process. Check the configured company organization exists in the local organizations table, otherwise new submissions may fail their foreign-key check. New records submitted while the configuration is absent have unknown ownership and require reconciliation. No migration has been applied to production.

For historical records, an authorized data owner must establish ownership from trustworthy source evidence, inventory null-owned records in each of the three tables, resolve conflicting existing `crm_source_links`, and prepare a separately reviewed, narrowly scoped reconciliation procedure. Do not bulk-assign by assumption. Verify counts and preserve originals; record who approved each mapping and its evidence. This repository does not contain an automated reconciliation job. Historical creation activity is not fabricated.

The lead activity table is append-only in normal application paths, not protected from privileged SQL updates or deletes. Assignment eligibility currently uses the synchronized `staff_memberships` mirror; check its synchronization and freshness against Clerk before relying on it for operational assignment. Authorization for actions uses the live Clerk session. Separate property intake is not yet available in the admin lead conversion UI.

## Reconciliation runbook for review

1. Before rollout, take and verify a recoverable backup and record the deployed migration journal, current application revision, organization ID, and counts of each source table. Test the whole procedure against synthetic data on a separate PostgreSQL instance.
2. After a reviewed deployment of the nullable columns, an authorized operator may use read-only queries such as `SELECT count(*) FROM leads WHERE organization_id IS NULL` (and the same count for `real_estate_enquiries` and `property_leads`) to size the unresolved queue. Restrict any export of identifiers or personal details to authorized staff.
3. Build a proposed mapping of source table and record ID to organization, evidence reference, reviewer and decision. Compare each proposed owner with existing `crm_source_links` and destination-client organization. Stop on conflicts or missing evidence; do not auto-assign unknown records.
4. Separately review a parameterized reconciliation transaction that updates only explicitly approved IDs where ownership is still NULL, verifies the source link and destination organization, records reviewer/evidence in an appropriate auditable store, and checks affected-row counts. Concurrent changes or mismatched counts must abort the batch. This document is not authorization to run it.
5. Reconcile in small approved batches, compare before/after counts, verify sample source links and keep the evidence and audit trail. Leave unresolved records NULL and inaccessible until reviewed. Do not backdate invented creation activity.

## Deployment and rollback gates

- Before any release: resolve and independently test duplicate-conversion concurrency; verify eligible staff against a test Clerk organization; complete authenticated browser tests, permission-negative tests and a clean isolated build. Inspect the actual deployment journal and schema for drift rather than assuming PGlite proves parity. Review both migrations, the conversion function, indexes, runtime privileges and backup recovery.
- In a controlled release, apply the reviewed additive migrations before deploying application code that reads the new columns. Confirm the configured organization exists, and monitor intake errors, unknown-ownership counts, lead conversion errors and CRM source-link consistency. The new lead list and dashboard intentionally hide unknown-owned historical leads until reconciled.
- If application rollback is necessary after migration, first assess writes since release: the previous application may not populate `organization_id` and may expose records without ownership filtering. A simple code rollback can therefore create unowned intake or change access boundaries. Pause or route intake safely, preserve activity and newly linked clients, and select a reviewed compatible application version or forward fix. Do not automatically drop the new columns, trigger, functions, tables, or CRM links; doing so can destroy new data or audit history. Database restore is a separate, approved operational decision with an explicit recovery point and impact analysis.

### Stabilization update

Do not proceed while the verified overlapping-conversion race or the unimplemented Clerk membership reconciliation remain open. The live Clerk check added to the lead update action is a fail-closed safeguard, not a complete synchronization solution. An approved client identity policy is required before adding a uniqueness or serialization rule; shared contact information alone cannot be assumed unique. The isolated real-PostgreSQL migration test passed, but deployed schema/journal comparison and reviewed reconciliation remain separate gates.
